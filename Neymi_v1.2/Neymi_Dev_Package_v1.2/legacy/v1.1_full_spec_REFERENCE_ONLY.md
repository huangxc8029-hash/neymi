# PART 1A — v1.1 重大设计与工程变更（优先级高于旧版示例）

> **日期** 2026-10-24；**命名** `Neymi` 仍为工程暂定名（未锁定商标，候选 Cyber Card 等不应触发源码批量改名）；**规范优先级**：本节及 `INTERACTION_AND_SHARING_v1.1.md` ＞ 本文其他旧版描述 ＞ v7/v8 HTML 视觉原型。v1.1 是对 v1.0 的继承性升级，不是重新立项。

## A. 已正式确定的产品决策

1. **名片外形仍为横版 `5:3`，姓名永久固定左上角，Company 与 Role 位于姓名下方。** 不默认印产品标志、二维码、卡号。头像和公司 Logo 变成由用户选择的可选媒体模块/装饰，不能强制出现，不能遮挡身份核心。
2. **取消固定六宫格、等尺寸六块与“最多显示六项”的业务规则。** 用户从自己的 30+ 类本地内容库挑选当前卡片要显示的入口；一页可能有 3、4、5、6、7 项，各项大小可不一样。超过当前模板的容量，应允许换排版/增加展示页/在翻面承载，而不是删除信息或缩小到不可读。卡片底层 schema 不设置全局 `maxModules=6`。
3. **边框大幅弱化**，优先用材料层次、半透明浮动玻璃块、留白、遮罩与景深创建点击区域；不用 Excel 网格线。每个入口默认只显示英文信息类目名，详情点击后才显示实际内容。
4. **主块可变**：用户可把 Story、Projects、Portfolio、Photo、Social 等任意模块设为 `featured`，获得更大面积。系统按布局样式和卡片宽高自动给其他模块分配空间；初版三套布局 `Editorial`、`Constellation`、`Ribbon`，不把布局尺寸写入个人资料数据。
5. **动效原型要求三种可切换、可比较的新效果**：`Floating Glass`（浮窗升起与景深）、`Piano Keys`（琴键级联/错峰轻弹）、`Orbit Reveal`（从点击位置环形揭露）。它们用于信息入口出现与进入详情；用户此前测试过的 Ring Reveal/Light Sweep/Soft Fade 只能保留为可选兼容方向，不能冒充新设计。遵循 `prefers-reduced-motion`，不采用频闪或强烈弹跳。
6. **展开详情的右上角附近放微型 Copy 角标**，图标紧挨所显示的字段，不在每个首页模块都堆复制按钮；返回只显示小型箭头图标（必须有屏幕阅读器标签与足够触控热区）。Contact 内 Phone/Email/Website 等结构化子项分别复制，未填显示 `No information available`。
7. **发送前 Share Sheet 是核心功能，不是后续装饰。** 用户每次选择要分享的身份字段与内容模块；Contact 可逐项选择 Phone/Email/Website，Social 可逐个平台选择。选择结果形成独立的 `share projection`；只有选中并获授权的字段被序列化/导出，没选中的字段连 JSON key、隐藏 DOM、SVG 文本和预览字符串都不能出现。
8. **Profile Library 始终为本地用户掌控**。服务端只保留公共模板、Sleeve 样式、授权凭证、唯一会员/编号发行记录及付款必要数据。用户输入的 Name/Phone/Story/Photo/Logo/Contact Library 不默认上传服务器；本地完成内容与样式组合。已付费的模板/Sleeve 可以在获取离线授权后本地离线渲染（加密备份与跨设备同步分别规划）。
9. **写真照与公司 Logo 可选、默认关闭**。严格处理媒体元数据（照片 EXIF/GPS）、高像素资产压缩、设计安全区、logo SVG 安全清洗及用户授权；不能为了生成服务器侧缩略图而默认上传用户图片。
10. **未来会员 Sleeve** 是包在完整 Card 外的一层独立数字封套：允许握手/笑脸/封印/线条动效和可签名可验证的限量身份视觉，但不能把它画到卡片内容块里。接收者可跳过动画直读名片。未付费 Guest 永远能自由收发、保存和回赠普通卡。
11. **现场交换接口**：PWA 优先 `navigator.share`、便携 `.ncard` 和 `.vcf`；Apple 设备 AirDrop 是 iOS/macOS **操作系统分享面板中的一种交付路径**，不是浏览器可任意调用的私有 AirDrop API；NFC 首版优先可选 NDEF 标签/兼容 Android 的 Web NFC 或实体 NFC 卡用于触发 HTTPS 落地页，不承诺 iPhone PWA 能任意写标签，也不宣称贴一下就完成指定人加密交换。OS/Web 兼容检测 + 显式回退是必做验收。
12. **本阶段不开发** Coins、社交 Feed、静默获取 WhatsApp/微信资料、付费才能导出自己的联系人。价格、正式品牌名、NFC 硬件 SKU 尚未确认。

## B. v1.1 概念模型与关键页面

```text
Device (Guest / Member)
  Profile Library (30+ local module kinds + local Photo/Logo assets)
            │
       Card Composer ── template selection ── local Card Renderer
            │                            └─ optional Sleeve Renderer (signed entitlement)
   Persona / Card Layout
            │
      Share Composer  ← 每次选择身份字段、模块、子字段、接收者/用途
            │
      Strict Share Projection  ← 只从用户许可的字段生成独立对象
            │
       ┌────┴───────────┐
       ▼                ▼
    .ncard / .vcf    OS Share Sheet (AirDrop / WhatsApp / 微信等作为外部通道)
          [不向业务服务器发送个人 Profile 明文]

Commerce API (optional, non-profile)
  Public template assets / Sleeve assets / Entitlement issuer / VIP serial registry / Payment
```

**业务对象分离**：`ProfileModule` 描述用户本地事实；`Persona` 定义公共身份外观；`CardLayout` 定义当前入口顺序、featured tile、布局预设、页面/翻面；`ShareDraft` 是单次分享中短暂存在的勾选态；`ShareEnvelope` 只包含经投影筛选的披露数据。`MemberCredential` 不包含真实名片资料。

**页面路径建议**：`/studio`（30+ 类资料编辑和名片配置）、`/preview`（可点击的实时卡片）、`/share`（发送前选择与接收方预览）、`/receive`（接收文件/链接、显式保存）、`/member`（可选付费封套/号码）。应用内网页保留 PWA 的无账户 Guest 流程。

## C. 版式布局规则（Card Composer）

- 卡容器：逻辑横版 `aspect-ratio:5/3`；`IdentityHeader` 约占高度 30–42%（依姓名长度自动调整），浮窗组位于其余区域，不能重叠。
- 每个模块入口只显示 title，可选极小状态提示；`ModuleContent` 不参与布局缩放，不在初态露出电话或长故事。
- 布局规格：将可用内容区域看成分数坐标网格（例：12 columns × 6 rows）。`Editorial`：主 tile 在左；`Constellation`：大 tile 在右、其余围绕；`Ribbon`：主 tile 横贯顶部，下方按权重分配。`featured` 可自由选择，其他项可重排。
- 建议一页 3–7 个入口；0 项则展示添加引导；1–2 项自动扩张；8+ 项自动启用分页/背面/滚动，但不得隐藏模块、降至不可读字号或裁剪必要内容。此范围是设计建议，不是后端 schema 限制。
- 动态高度：真实手机 360/390 px 宽下仍保持横版比例，触控热区需进行单独可用性验证；屏幕阅读器可直接访问每个入口；连续信息可以在详情里滚动。
- 无需框线表示边界：浅色透明浮板 + 轻微模糊 + 金色边界只在 hover/focus 展开；不强制统一大小。高级质感优先于大量发光特效。
- 个人照片可位于内容块、全景背景或详情页，公司 logo 仅作为轻量品牌标识；没有媒体信息时不显示空容器。

## D. 动效时序、触发与无障碍

| Motion | 入口出现 | 点击展开 | 时间建议 | 退出 |
|---|---|---|---|---|
| Floating Glass | 透明度 0→1，translateY 18–24 px，blur 5 px，缩放 .92→1 | 自点击块位置抬升浮窗，周围轻微虚化，详情占据卡片内容层 | 420–650ms | 对称淡出；焦点返回原模块 |
| Piano Keys | 每块 stagger 60–85ms；Y 轻弹、X 轴轻微倾斜 | 附近块轻位移让位，主信息以弱弹簧进入；禁止大幅跳跃 | 460–650ms | 轻收拢 |
| Orbit Reveal | 沿短轨道漂浮进入，按序展示 | 从点选中心由小到大环形揭露，星环柔和响应 | 450–620ms | 圆形遮罩收回 |

**实现要求**：动效是纯视觉层，不影响数据投影。避免 `setTimeout` 作为业务状态同步唯一依据；React 建议用状态机：`overview → revealing(id) → detail(id) → closing → overview`。在 `prefers-reduced-motion: reduce` 下去掉变换，仅保留瞬时状态。长字段字体不小于可读阈值（响应式 rem/clamp）；长篇 Story 在详情滚动，不截掉内容。

**Sleeve 动画（独立商业模块，当前只规定规格）**：`SEALED → OPENING → REVEALED`，封套可选 Handshake Line、Smile Draw、Wax Seal Glow；静态封套图片仍具辨识度，重复查看可选择跳过，会员符号/证书有效性验证与动画不耦合。禁止把 GIF/Canvas 当作真会员证明。

## E. 分享前字段选择与隐私投影（P0）

### E1. 用户流程

1. 编辑资料时，用户为每条 `ProfileModule` 设默认公开级别（private/public/restricted），但**发送前不是自动发送资料库所有公开信息**。
2. 点击 `Choose & Share` 打开一次性 `Share Composer`：可选择 Name/Company/Role 是否发出；从**全部已经授权的资料**中选择模块（不一定必须正显示在此卡的首页）；Contact 与 Social 展开子字段复选框。Phone、精确 Location 默认不勾选；图片必须单独勾选。
3. 在同一页面显示实时 **Recipient Preview**，呈现的是严格投影后的数据；切换某个复选框应立即影响接收者预览和实际导出字节。
4. 点击 Share / Download .ncard / Export vCard：这些入口必须消费**同一个不可变的 `ShareProjection`**，不得各自手写不同的过滤规则；导出之后不给未授权字段留占位。
5. Recipient 在无注册的 Reader 中读取收到的子集；不假设原发送者资料可以远程拉取更多字段。

### E3. 端到端验收

- Phone 未勾选：`.ncard` 内容、`.vcf`、系统分享文本、接收者预览 **均无号码及 phone 字段**（不仅不可见）；电话号码勾选后，在 Contact 内正确输出。
- Social 勾选 LinkedIn、取消 Instagram/X：只输出 LinkedIn，不能以自由文本一股脑输出所有平台。
- 不勾选 Story，即使它出现在当前名片主卡首页：不发 Story 值；用户可单次选择一个当前首页没有展示的授权模块。
- 关闭 Share Composer，不会修改个人资料和卡面布局；默认选择严格遵循“最少披露”原则，不暗中重置为全选。
- 如涉及照片/Logo，未勾选不得以任何形式进入导出 payload；即使勾选，移除 EXIF 位置信息。
- 受限字段在未完成可信接收者公钥确认/加密前 **不能以明文分享**。完整的指定接收者加密仍属于独立安全里程碑，不得声称 v1.1 原型已实现。
- 文件分享/扫码/NFC/外部聊天渠道是**交付载体**，不等于访问控制。通过 AirDrop 发送的纯明文 vCard 仍然是明文。

## 0. 决策摘要（Codex 必须优先执行）

Neymi = **无需注册即可制作、接收、保存、回赠和分享数字名片**的 local-first 工具。卡片数据归用户，基本隐私安全对所有人免费；用户可从 30 类模块任选内容，横版模板根据布局动态展示**可变数量和不等尺寸模块入口**（建议一屏 3–7 个，更多可翻页）。只有购买/受赠有效邀请码并完成核销后，才成为付费 Member，领取可验证的 **Identity Sleeve** 和高级设计权益。

### 0.1 已确定要求（不擅自修改）

1. 普通用户叫 **Guest**：不注册、不付款、不要求手机号/邮箱、无需下载 App 也能创建/接收/回赠基本名片。用户点击一张别人发来的名片后，不应因“回赠”而遇到注册墙。
2. `Card` / `Profile Library` / `Membership` / `Identity Sleeve` 是**四个独立概念**。购买 Sleeve 不改变名片个人资料所有权；删除会员权益不影响免费名片读取。
3. 免费提供 **6 个具有专业审美的横版模板**（黑、白、粉、蓝、橘、绿），没有强制按性别区分，任何人可使用任意模板；初版最先打磨 **Cosmic Black（黑洞 / 银河）**。
4. 卡片比例取传统名片 `90:54 = 5:3`，为数字画布的逻辑比例；**无强制人像、无强制二维码、无制造工具的醒目 Logo**。用户可另行导出联系人或使用分享按钮。
5. `Cosmic Black` 卡左上角始终展示 **Name / Company / Role**（用户没填的行隐藏），下面为**可变尺寸、可变数量的可点击浮动模块区块**（不强制 2×3）；区块平时**只显示标题**（如 Location、Story），绝不能同时铺满详细内容。
6. 点击区块后整张卡的内容层**变成该类信息的详情大屏**；左上角姓名与公司/职业保持固定，不随意移到右上角。详情显示结构化内容；无内容提示 `No information available`，已发布的名片应默认不出现空块。
7. 详情中每个可复制的数据**旁边右上角**放一个非常小的 copy glyph（视觉 12–14 px，实际点击热区至少 36×36 px，可在紧凑卡中通过透明热区实现）；返回只保留**箭头图标**（同样有足够命中面积），不出现大号按钮或文字“返回名片”。
8. 用户不是只能选 6 类：**30 类可选信息目录 + 用户可自定义类别**，模块可重复实例化；用户在信息库可存很多资料，在某张卡上动态排布多个（不限定六个），能添加、编辑、隐藏、排序、替换和在不同 Persona 中复用。
9. `Contact` 是**复合结构**，含 Phone、Email、Website 等子项，逐项复制/可选打开系统应用；`Social` 是带平台名、handle、URL 的记录数组，不能只是一长段不可点击文本。
10. 卡片支持 `Floating Glass` / `Piano Keys` / `Orbit Reveal` 三种信息展开动效，遵循减少动态偏好；**Identity Sleeve** 的封套/打开动画另成一个组件和付费权益，不要混为一谈。
11. 普通交换免费；只有邀请码兑换产生 **Member**；邀请码既可自购，也可购买送人。会员支付是一次性权益的起点，不强制收集名片明文、社交图谱或实名认证。
12. 首发采用 **PWA Web**；iOS/Android 原生 App 作为后续可选路线。标准 `.vcf` 文件导入/导出与系统确认是第一版实用能力，不承诺第三方网页直接静默写入通讯录，也不承诺从微信/WhatsApp 自动读取好友个人资料。

### 0.2 本轮明确不做

**Coins/代币、余额充值、抽奖红包、二级号码市场、实名 VIP 证明、Feed/社交网络、AI Resume、CRM、全面相机扫描 OCR、后台明文通讯录同步、陌生人名片实时云搜索、自动拉取微信/WhatsApp 账号资料、强制头像/二维码。** 只为未来扩展保留接口，不在首版实现。

## 1. 用户与用户任务

### 1.1 角色

| 角色 | 含义 | 权利 / 任务 |
|---|---|---|
| Guest Creator | 未注册本地用户 | 免费建卡、编辑、导入现有 vCard、导出、分享、备份 |
| Guest Receiver | 名片接收者 | 无登录预览、保存到 Neymi 本地、另存到系统联系人、回赠 |
| Signature Member | 成功兑换有价邀请码的会员 | Guest 全部权益 + 会员证书、Identity Sleeve、高级主题、更多 Persona |
| Gift Sender | 自购/赠购邀请码者 | 付钱买券、下载/发送不含个人资料的礼物凭证，不获得收礼人的联系人 |
| Publisher Admin | 发行方运营人员 | 管理商品、系列数量、订单争议和发行签名，不管理私人卡片内容 |

### 1.2 关键端到端用例

**UF-01 免费自建**：访客打开页面 → 选模板 → Name（必填仅在需要对外成卡时），Company/Role 可选 → 通过目录添加模块 → 调整 6 区块 → 本地保存 → 查看/分享。过程中不请求 `signup/login`。

**UF-02 A→B 交换**：A 选择允许分享的内容 → 发公开名片文件/兼容链接或 vCard → B 打开 → 保存 → B 点击 `Send My Card Back` → 用 Guest 免费创建并回赠。**不能因无 Member 权益而无法收/发/回赠**。

**UF-03 模块编辑**：用户保留 20 个模块，选 6 个上卡；把 `Hobbies` 换成 `Talents`，原数据仍存于信息库；切换主题不改变内容。添加 `Contact` 不需要为了 Phone/Email/Website 占 3 个卡位。

**UF-04 信息展开**：点击 `Projects` → 动画从所点区域发生（或选择另一动效）→ 显示项目列表 → 选某一项复制/打开链接 → 右上角小箭头关闭 → 保持名片状态与聚焦位置。

**UF-05 系统联系人**：用户点击 `Save to Contacts` → 系统下载/分享 `.vcf` → iPhone/Android/桌面通讯录由用户**确认导入**；`Import vCard` 允许从文件读取自有联系人字段到编辑器，经用户确认映射和权限，不自动公开。

**UF-06 付费邀请码**：Guest 预览 Sleeve → 自购或受赠 voucher → 后端验证支付/一次性核销 → 本地生成独立会员密钥 → 服务端签发 member entitlement 与 Sleeve 证书 → 本地导出恢复包。Guest 数据库不包含支付身份的直接字段。

**UF-07 恢复**：新设备通过加密备份恢复 Profile Library、Persona、会员私钥与凭证（有明确失败/密钥丢失提示），不可要求上传私人资料明文才能恢复。

## 2. 内容信息库：30 种基础类型（用户可添加自定义）

**核心数据模型不固定六字段。** 卡片只保存模块引用与展示位置；资料库保存一个人填写的全部模块。允许多个同类型实例（个人/工作 Contact、不同项目）。用户可以重命名区块标题，底层 `kind` 始终规范化，不随 label 改变。

| 组别 | 模块类型（英文 UI 名） | payload / 内容结构关键字段 |
|---|---|---|
| Identity & Connection | **Location** | city、region、country、remote; 不默认高精度定位 |
| | **Contact** | phones[]、emails[]、websites[]，每项 label、value、visibility |
| | **Phone** | phones[]: label, E.164 preferred number |
| | **Email** | emails[]: label, address |
| | **Website** | links[]: label, https URL |
| | **Social** | accounts[]: platform, handle, https URL |
| | **Links** | links[]: title, URL |
| Personality & Life | **Story** | title, body（纯文本或受限富文本） |
| | **Hobbies** | activities[] |
| | **Interests** | topics[] |
| | **Talents** | items[]: name, note |
| | **Values** | statements[] |
| | **Languages** | languages[]: language, proficiency（可选） |
| | **Life Motto** | text |
| Work & Creativity | **Projects** | projects[]: title, summary, URL, dates? |
| | **Experience** | positions[]: role, organization, start/end, summary |
| | **Skills** | items[]: label, level? |
| | **Portfolio** | projects[] / link[], optional media metadata |
| | **Services** | offerings[] |
| | **Education** | school, qualification, dates |
| | **Certifications** | name, issuer, issuedOn, verificationUrl? |
| | **Awards** | name, issuer, year |
| | **Publications** | title, type, URL |
| Community & Beyond | **Volunteering** | organizations[] |
| | **Community** | groups[] |
| | **Causes** | topics[] |
| | **Events** | event entries（仅用户主动填写） |
| | **Collaboration** | subjects, availabilityNote |
| | **Availability** | hours/description, publicContact? |
| | **Custom Section** | label, blocks[] |

**扩展规则：** MBTI、星座、生日、头像等未来可加，但第一版不强制且不应把敏感个人属性设成默认公开；`Custom Section` 可覆盖长尾需求。填写建议应根据用户选择的场景（Business/Creator/Personal）个性化，但不能替用户自动公开内容。

### 2.1 名片上默认六宫格

动态模板初始建议：`Location / Story / Projects / Social / Contact`（通常 5 项）。**不是全体用户固定要求**，可替换为 Talents、Experience 等任何实例。`Interests` 可作为备选。原则：**入口个数由可变布局决定，不是数据字段总量约束**。

- `Contact` 里面包括 `Phone + Email + Website`（不存在的子项不渲染或在编辑模式提示）。
- `Social` 点击后可分别对 LinkedIn、Instagram、X、个人博客等条目打开/复制；不能把所有资料压成无交互的长句。
- `Story` 和 `Experience` 长文不应强迫缩到 8px；展开后可滚动/分页浏览，封面区仍保持水平名片比例。
- 若模块在资料库存在但未授权公开，卡片**不得**仅靠 CSS 隐藏它：导出的公开 payload 中必须根本不存在该字段。
- 用户可以将 6 槽排成 3×2 的默认布局，后续模板可采用大小不等的组合，但**内容模型不得依赖格子数和布局**。

### 2.2 内容编辑器（关键页面）

采用双栏：左侧/上方是 live preview，右侧/下方是资料编辑；手机竖屏按**预览—选择目录—编辑详情—发布**的流程布局。编辑流程：

1. **Identity Header**：Name / Company / Role（公司、职业缺省时隐藏，不预置真实资料）。
2. **Content Library**：30 类按 4 组折叠，搜索，`+ Add`，支持重复模块、草稿、本地保存。
3. **Edit Section**：模块专用表单（Contact 不用一个大 textarea 代替 phone/email/site），可设置 title、公开范围、内容、在卡上展示或仅保留资料库。
4. **Select & Arrange**：6 槽选择、替换、拖拽或键盘上下移动、禁用项原因提示；新增第七项时提醒选择隐藏一个，不删除数据。
5. **Live Card**：可真实点开、复制、返回；支持三种动画切换供设计测试。动画配置是 UI 偏好，不能作为数据可见性权限。
6. **Save & Export**：本地保存、备份/恢复、分享前权限预览。HTML v8 的导出纯 JSON 只能用于**演示**，正式用户备份必须加密并清晰标识。

## 3. 卡片视觉系统与交互定稿

### 3.1 Card 基础形态

- **逻辑尺寸**：横版 `90×54mm` / CSS `aspect-ratio: 5 / 3`；网页以相同比例缩放，不必模拟实物纸边占满屏幕。
- **禁止**：固定竖版、内嵌人像头像、默认二维码、NE YMI/工具品牌占据主视觉、大面积静态信息列表、各方块同时写出全部值、把特殊会员编号贴在姓名下面。
- **固定身份区**：左上，按 `Name`、`Company`、`Role` 三层视觉优先级。**姓名不受详情切换影响**。
- **动态信息浮窗**：身份区下方按 Editorial / Constellation / Ribbon 可变排布，3–7 项优先；初态仅显示英文类别标题，留白充足且边界克制，使用低对比边框而非粗重按钮。表面背景是主题的独立视觉层。
- **详情层**：替换六格的主要显示区域（可延伸覆盖主要画布），保留姓名固定区；结构化字段可分行/分组展示，不一味拉大所有字体。
- **点击**：鼠标、触屏、键盘 Enter/Space；详情中的关闭箭头可以 Escape 返回；离开详情时焦点回到刚才的 tile。
- **复制**：信息值后的右上角 12–14 px 小型 `copy` 图标；Contact 每个 Phone/Email/Website 子项一个，空字段不显示复制图标；视觉角标虽小但点击热区建议不少于 36px，理想 44px。
- **公开展示**：未填写模块默认隐藏并可显示占位引导（仅编辑器）；预览中显式测试空状态时返回 `No information available`。

**视觉：** `#06080D` 深背景，暖金 `#D8BB8C` 点缀，白色偏暖 `#F4EEE6` 文本；宇宙/星环在背景右半部，**不能盖住正文与点击方块**。背景是**低优先级视觉层**，图片仅在不包含隐私信息时作为静态资源；允许通过 CSS 渐变/轻量 WebP 实现质感，避免首屏大型视频。

### 3.4 付费 Identity Sleeve（非 Card）

- Sleeve 是数字封套／蒙板，**包在独立名片外围**。脱下 Sleeve 后，Card 仍是完整标准比例、可保存/导出的名片。
- Sleeve 承载高级材质、特殊符号、少量限量编号、发行者签名验证标识；**不要把大编号和会员等级强塞进名片的信息区**。
- 会员注册 = 付费邀请码兑换并生成可验证权益，不允许因未付费限制基础建卡或交换。
- 静态外观也必须好看：聊天软件分享预览不承诺播放动效。发送者可选择“直接看名片”绕过封套；接收者也可跳过打开动画。
- Sleeve 视觉资产可由官方签名证书引用/授权，不应要求读者每次访问运营服务器才能显示已获得的纹理。

### 3.5 动画规格（详见 `DESIGN_AND_MOTION.md`）

**名片模块 3 种信息揭示效果：**

- `Ring Reveal`（默认候选）：以被点 tile 的中心为原点，圆形遮罩（clip-path）由 0 展开至覆盖详情；**520–620ms**，缓出，反向退出 260–340ms。黑洞主题可以有轻微光环响应，不要让内容忽大忽小。
- `Light Sweep`：柔和光幕水平方向扫入/退出，**450–550ms**；必须避免强烈白屏闪烁、频闪。
- `Soft Fade`：轻微 blur 与 opacity 的组合，**300–450ms**，小幅位移/缩放 `<3%`，更通用、更加稳重。

**Sleeve 单独动效**：入场显现 → 拆封/抬起 → 拉出独立 Card → 回到完整 Card。默认可跳过，全部非必须，不应阻碍保存与回赠。`prefers-reduced-motion: reduce` 时改瞬间状态切换或极短淡入。

## 4. 共享和 Contacts 互操作

### 4.1 不夸大能力

**公开卡 ≠ 仅指定接收者可看。** 任何拿到完整公开分享包的人都可能复制、转发。包含私密数据的交换需要**对接收者公钥加密**，不能用“链接私密”的文案替代权限系统。微信/WhatsApp 通常支持发送链接或 vCard，但普通 PWA **不能任意读取微信号、好友列表或第三方账户个人资料**。

### 4.2 第一版分享顺序（务实可行）

1. **vCard .vcf**：导出用户明确选中的 Phone/Email/Website、FN/ORG/TITLE，规范 escape 和折行；不塞 Story 全文或本地私密模块。提供 4.0 标准实现和经设备测试的 3.0 兼容导出兜底。
2. **可移植 card package**：公开子集封装为带 schemaVersion 的 `.neymi-card.json` 或 `.ncard` 文件，接收端无需账户打开；分享/接收可使用操作系统分享菜单（支持时）或文件发送。
3. **低数据量公共链接**：可选通过片段 URL（`#payload=...`）携带**已授权公开**的精简卡片，静态读取器在本机解析；不得声称接收平台无法读取被转发链接。链接过长时退回文件共享。无服务器托管个人主页不保证平台生成含个人信息的富链接预览。
4. **可选公开托管（后续）**：仅用户明确选择将公开资料放到自己或第三方托管的地址时启用；不得把默认公开上传包装成“绝不上传”。
5. **指定接收者加密（独立里程碑）**：获取/验证接收者公钥、认证握手、版本化加密包和成功解密测试，成熟后再对外称为 E2EE。

### 4.3 Contacts 和第三方应用

- `Import from vCard`：本地读取 `.vcf`，展示导入前预览、重复项处理和字段可见性选择；不得导入后直接公开。
- `Save to phone contacts`：生成 `.vcf`，交给系统联系人 App **由用户确认保存**。不要在网页上承诺无需确认即可直接写入系统通讯录。
- 微信 / WhatsApp：支持通过系统 Share Sheet、文件或链接发送；“从微信/WhatsApp 一键导入别人的个人资料”**首版不可依赖，未找到通用授权 API 的实现基础**。
- `Contact` 展开支持 `tel:`、`mailto:`、`https:` 用户触发的动作；复制和打开操作分开，禁止复制按钮意外打开电话/外站。

## 5. 付费会员、邀请码和稀缺标记

### 5.1 免费 / 付费边界

| 能力 | Guest | Signature Member |
|---|---|---|
| 无注册建卡 / 读取 / 分享 / 回赠 | 是 | 是 |
| 私人资料所有权与基础加密备份 | 是 | 是 |
| 当前单 Persona + 6 套正式免费主题 | 是 | 是 |
| 可编辑 30 类资料库 + 自定义字段 | 是 | 是 |
| 专属 Identity Sleeve、发行编号与签名证书 | 否 | 是 |
| 付费模板、额外主题风格/配色/动效 | 否 | 是 |
| 多 Persona、定制页面布局等高级功能 | 可先受限 | 是 |

**基线安全和数据出口永远不设付费墙。** 第三方交易服务可能收集必要的付款资料，Neymi 不把这些资料复制到 Card Vault。

### 5.2 资格流程

Guest → 看 Sleeve（无须账号）→ 自购或收到礼物码 → 支付侧 webhooks 确认 → 发行一次性 Voucher → 本地生成独立的 `memberKey` → 原子核销 `REDEEMED` → 签发 `SleeveCertificate` → 本地持有和恢复。未经支付的用户不能自行发行真正有效的 Signature 证书。**展示编号不是兑换密码**。

### 5.3 原型中应测试的情况

- 同一笔付款 webhook 重放 10 次，按商品数量发放**恰好** N 张券；不能创建多余序号。
- 同一个 voucher 在两台设备并发兑换，只能有**一个成功**。
- 付款未成功时，不能仅凭前端返回页发放资格。
- 服务端不应保存名片姓名/故事/个人 Contact 的明文。
- 假造一个外观一模一样的 Sleeve 截图，也不能通过数字签名验证；离线验证证书与实时撤销/持有人控制权验证要区分。
- 退款、Chargeback、礼物误转发、备份丢失要有明确状态和处理方案。

**发行上限、售价、Gift Pack 和 Founding Edition 等属于待验证商品策略，不把 $9.99/$29 视为已确认价格。** 不得对稀缺编号做投资价值/升值承诺。

## 6. 技术架构（Web-first）

```text
[Guest / Member Browser PWA]
  ├─ React UI: Studio, Library, Card Renderer, Card Reader, Contacts
  ├─ Dexie/IndexedDB: private profile + card layout + locally received cards
  ├─ Crypto adapter: backup encryption / signing / later recipient E2EE
  ├─ Import/Export: .vcf, .ncard, encrypted backup, static preview
  ├─ Member wallet: separate local key + signed entitlement certificate
  └─ Local rendering: 6 themes + independent Sleeve renderer
           │  (only commerce/public config/certificate; NOT card plaintext)
           ▼
[Hono/Node TypeScript API]
  ├─ Products, Orders, PSP signed webhooks
  ├─ Voucher issuance / atomic redemption / rate limiting
  ├─ Series numbering + signer / verification key publish
  └─ Anonymous member entitlement / revocation metadata
           ▼
[PostgreSQL]  [Payment Service Provider]

[Card transport] user-chosen messenger, file, local-only public link
  -> Receiver browser/PWA -> read, save, import, return a card (no account)
```

**工程首选**：`pnpm` monorepo，`apps/web` React + Vite + TypeScript + Tailwind/CSS variables；`apps/api` Node + Hono（或团队熟悉的精简 Node 框架）；`packages/domain` Zod Schema + typed models；`packages/card-core` 导入导出与投影；`packages/ui` Card/Tile/Detail/Sleeve；`packages/security` 已审查加密原语封装；PostgreSQL + Drizzle；Dexie IndexedDB；Vitest、Playwright、axe 检查、CI。**避免一个 demo HTML 的内联 JS 成为生产架构。**

**不推荐一开始做**：把整个 Profile 放在 NextAuth 用户表、把聊天/关注关系汇入后台、写自研密码算法、未测试的 WebGL 重 3D、两套不同名片 JSON 格式。

### 6.1 前端页面

| Route（建议） | 主要职责 | 需要登录吗 |
|---|---|---|
| `/` | 产品介绍、免费 Create / Open 卡片、模板画廊 | 否 |
| `/studio` | 身份区编辑、30 类信息库、六宫格编排、实时预览 | 否 |
| `/cards/:localId` | 本机已有卡编辑（本机 ID，不能直接当公众地址） | 否 |
| `/open` | 文件/片段导入，接收公开卡、保存和回赠 | 否 |
| `/templates` | 免费模板预览与购买 Sleeve 展示 | 否 |
| `/signature` | 会员权益和 Sleeve 外观预览 | 否 |
| `/checkout` | 商业订单，不携带 Profile 明文 | 否（自购/赠购） |
| `/redeem` | 兑换 voucher、本地会员密钥、签名权益 | 否（voucher 所有者） |

### 6.2 安全架构的交付边界

本地 `IndexedDB` 持久化并不天然等于用户数据已受到强加密：脚本、恶意扩展、被盗设备和浏览器清理都存在风险。生产层应设计**解锁/密钥/备份**方案并写威胁模型。即使后台不存卡片明文，访问原站点时加载的前端 JS 仍有理论访问权限，因此对“服务端绝对无法看到”的营销承诺须非常克制。

建议分阶段：
- **M1** 本地优先，默认不发数据到商业 API；导出加密备份供用户自主管理，用户明确允许的公开字段可独立分享。
- **M2** 独立 Member/Voucher 业务，敏感个人资料完全不在请求体出现。
- **M3** 经过安全评审的 recipient-specific E2EE，及长期可验证构建/独立解析支持。

## 7. 性能 / 无障碍 / 国际化

1. 初版 UI 文案以**英文**为首选（Name、Company、Role、Location、Story 等），可后续添加 i18n；技术文档中文。
2. 手机 320px、375px、390px、428px，平板 768px，桌面 1024px、1440px 必须实际验收；横版卡比例不变，编辑器布局可改成垂直结构。

6. 网络断开时仍可编辑已打开的 PWA 和本机卡；商业支付/兑换不可用时展示可重试状态但不影响 Guest 核心流程。
7. 非用户主动操作时不要触发系统拨号、跳转社交应用、网页 Push 权限提示。

# PART 2 — 设计与动画工程规范

# Neymi — UI 设计系统、黑洞名片与动画工程规范

> v1.0 · 2026-10-24。工作说明：这里是**可实现的界面协议**，不是给用户看的图片描述。早期参考图尚未过视觉验收；Codex 必须实际呈现并通过截图审核。

## 1. Design Principles

**Editorial First / User Identity First / Privacy by Design / Delight Without Delay**。

1. 持卡人是视觉主角。名字、身份、信息关系优先于装饰。卡面不默认出现 Neymi 字样、付费编号、系统状态或二维码。
2. 名片像经过平面设计师打磨的 90×54 mm 横版艺术品；不是个人主页压缩图，也不是“六个按钮 + 标签说明”的后台卡片。
3. 六个格子**只标栏目名**；不把公司名、邮件、社交 handle 同时填进格子。详情页可以是组块式编辑排版，而不是六行表格。
4. 背景不抢内容：黑洞/星河纹理低对比，文字要稳定可读。免费模板也须美观，不靠刻意做丑来驱动购买。
5. Motion 是信息切换的反馈，轻、短、可关闭；不拿动效阻断一键保存或回赠。

## 2. 版式解剖 — Cosmic Black

```text
┌──────────────────────────────────────────────────┐
│ Alex Chen                                        │
│ ROBOFOTO                                         │
│ Founder & Product Builder                        │
│                                                  │
│ ┌────────────┐ ┌────────────┐ ┌────────────┐     │
│ │ Location   │ │ Story      │ │ Projects   │     │
│ └────────────┘ └────────────┘ └────────────┘     │
│ ┌────────────┐ ┌────────────┐ ┌────────────┐     │
│ │ Hobbies    │ │ Social     │ │ Contact    │     │
│ └────────────┘ └────────────┘ └────────────┘     │
└──────────────────────────────────────────────────┘
```

显示名字、公司、职业为身份区，原则上固定左上；6 槽下方为标题块。**Detail 状态**：六格被详情层取代，左上 identity 仍可见，右上极简 back chevron；详情主体位于中央/中下区域，项目/社交/联系人可以各自采用最适合该类型的结构。

### 2.1 逻辑几何与字号

| 项目 | 大屏卡容器（900×540 CSS 逻辑画布） | 移动端 360px 缩放原则 |
|---|---|---|
| aspect ratio | 5:3 | 不随意变为竖卡；详情可使用外部弹层来解决长内容 |
| card safe padding | 4.8–6% width | 不小于 12px 实际 CSS |
| Name | 56–72px，根据姓名长短自适应 | 24–35px，最大 2 行，溢出处理 |
| Company | 12–15px / uppercase small tracking | 9–11px |
| Role | 13–16px | 9–11px |
| tile title | 19–24px | 11–14px（需真实设备判读） |
| tile gap | 10–14px | 4–7px |
| 详情主标题 | 36–64px，内容类型独立 | 20–32px，避免长电话和链接溢出 |
| copy glyph | 12–14px SVG | glyph 11–13px；点击热区放大不影响布局 |
| back glyph | 14–16px | glyph 14px；热区 36–44px |

**这里不是强制像素成品**；应按真实端口做视觉 QA，必要时将点击热区增加但保留极简视觉。

```css
  --cosmic-bg: #070911;
```

## 3. 模块详情的设计不应该“全部一套列表”

| 模块 | 详情排版建议 | 点击动作 |
|---|---|---|
| Location | 一个大城市/地区 + 次要说明，远离精确家庭坐标 | copy location，用户主动打开地图 |
| Story | 1–3 句大字号导语，后接滚动小段落，文章风格 | copy story |
| Projects | 大标题卡 + 项目摘要 + 链接，不按邮件列表样式强排 | copy link / open site |
| Hobbies / Talents | 横向排布或疏密错落的关键词排版，有层次的 tag typography | copy group/item |
| Social | 平台名称 / handle / link 三要素，分组布局，单独可点击 | copy handle / open platform |
| Contact | Phone / Email / Website 独立子栏，采用清晰的编辑版式，逐项 copy | copy specific / tel / mailto |
| Experience | 时间线 / 职位分组，避免把 20 年履历缩进一张 5:3 卡 | scroll detail or open expanded view |
| Custom Section | 根据 payload blocks 选择文本、条目和链接等有限安全组件 | copy selected field |

所有详情不展示系统填造的虚假资料；在编辑器允许空值提示 `No information available`；对外只呈现经用户批准分享的条目。

## 4. 三种信息揭示动画（实装互相可切换以做 A/B 审美测试）

### Motion A — Ring Reveal（默认候选）

点击 tile 的中心位置计算 `(originX, originY)`；`clip-path: circle()` 从该点向外扩散覆盖画布。星环亮度轻微提高（opacity + ≤0.08），**不要**出现发光爆炸或使信息字快速缩放。

- Open：520–620ms，缓出 `cubic-bezier(.18,.93,.28,1)`。
- Close：260–340ms，可反向圆形回缩至原始 tile；取消任务中的动画不会留下隐藏的点击遮罩。
- Detail 初始不可点击，展开完成后 focus 到详情标题/首个动作。
- 小于 360px 或低性能浏览器：如 clip-path 性能差，自动使用 Soft Fade。

示例 CSS（实现时不要在整个 viewport 上多层 blur）：

```css
.detail--ring.is-entering {
  clip-path: circle(0 at var(--origin-x) var(--origin-y));
  animation: reveal-ring 560ms cubic-bezier(.18,.93,.28,1) forwards;
}
@keyframes reveal-ring {
  to { clip-path: circle(150% at var(--origin-x) var(--origin-y)); }
}
```

`150%` 对任意原点可能不足以覆盖所有四角：**最终生产实现需按最远角距离计算像素半径**，或保守使用比 150% 更大的安全值并测试四角。

### Motion B — Light Sweep

从被点 tile 水平位置向卡右侧，扫过微弱金色高光后详情进入，不用白色闪屏。扫光装饰建议独立在 `transform` 层动，内容透明度 0→1。

- Open：450–550ms；Close：250–330ms。
- 禁止每 60ms 闪一下、持续扫光循环、过量 `filter: blur`。
- 减少动态时关闭扫光。

### Motion C — Soft Fade

推荐默认低性能设备、通用浅色模板。透明度 0→1，小幅 translateY(5–8px) 或 scale(.985)→1，必要时低量模糊；避免读者感觉卡片跳动。

- Open：300–450ms；Close：180–260ms。
- 详情可在画布上静止，只有文字层淡入。
- 目标是“高档 UI 的克制动感”，不是魔幻转场。

### 4.1 动画控制及无障碍

- `animationPreference = 'ring' | 'sweep' | 'fade'`，先在设计测试 UI 中暴露，正式版可固定默认或从用户偏好读取。
- `prefers-reduced-motion: reduce` 时 0–80ms，立即更新 UI，无扫光、旋转。
- 快速双击、动画进行中再次点击其他格子，应以**最新一次操作为准**并正常清理动画，不能出现“双重详情层”。
- `Escape` 关闭详情，back chevron 有 aria-label `Back to card`，焦点回到触发 tile。
- 复制角标 visually 12px，但需可点击热区；键盘可聚焦并有 aria-label `Copy email` 等；成功提示使用不打断用户的 aria-live。

### 4.2 结构化 Contact 动效示范

Detail 展开后，Phone/Email/Website 以 40–60ms 的 stagger（可选）顺序进入，但整个详情完结不超过 650ms。小图标位于**对应内容后右上方**，不能放到入口 tile 上，也不是放在详情顶部的巨大复制按钮。Telephone 若缺失则不显示可复制内容；编辑测试时可显示 `No information available`。

## 5. Paid Sleeve 的不同动作系统

| 状态 | 动画 | 触发 | 失败/跳过 |
|---|---|---|---|
| `SLEEVE_IDLE` | 外封套静态细节、极轻高光 | 首次展示 | 完全不动也漂亮 |

# PART 3 — 数据模型与 API

# Neymi — 数据模型、API 契约与文件格式（可编码规格）

> v1.0。目标：让 Card、Profile Library、View、Member 和 Sleeve 彼此独立。示例 TypeScript 为**目标契约**，不是声称已在原型中实现。

## 1. 数据分层

```text
[PrivateProfile] 本机：真实拥有的内容/偏好，含未公开资料
  ├── IdentityHeader (name, company?, role?)
  ├── Sections[] (30-kind registry + multiple instances + custom)
  ├── Cards[] (persona and per-card 6 displayed section refs)
  └── ReceivedCards[] (对方授予查看的已收名片)

[PublicProjection / share envelope] 每次明确选择后生成
  ├── identity header: 已授权内容
  ├── section projections: 只包含本次分享范围的字段
  └── format version + optional integrity signature

[MemberWallet] 本机独立容器
  ├── entitlement signing key pair / key handle
  ├── certs[] (sleeve/license certificate)
  └── backup/restore metadata

[Commercial Backend] 不存个人 Profile 明文
  ├── product and edition catalog
  ├── order / PSP transaction reference
  ├── voucher digest / lifecycle
  ├── membership public key and certificate issuance
  ├── edition serial allocation
  └── signer public keys and revocation metadata
```

## 3. Schema Validation and Registry

`packages/domain/src/registry.ts` 每个 `kind` 定义：`id / label / group / defaultPayload() / zodSchema / detailRendererKey / maxPayloadSize / vCardMapping?`。自定义栏目仅支持受限富文本或数组结构；不接受原始 HTML、JavaScript、嵌入 iframe。

**Section cardinality**：同种 `kind` 可添加多个实例，`Section.id` UUIDv4 或其他本地随机稳定 ID。用户切换主题只修改 `templateId`，不要删除 `sections`。六槽限制仅由 `cosmic-black.layout.maxSections === 6` 决定，不能写死在 Profile 层。

## 5. 分享文件格式

**Public `.ncard`**：版本化 JSON / CBOR 包，最小有 `format, schemaVersion, card, exportedAt?`，可选签名/校验；不得在导出时附带 Profile 私有模块、会员 secret key、完整联系人库或隐形“分享者 ID”。未来提供开放格式说明和第三方读取 SDK。

**vCard**：依 RFC 6350（4.0），兼容部分设备所需的 vCard 3.0 导出；姓名至少 `FN`，可映射 `N / ORG / TITLE / TEL / EMAIL / URL`，换行和分隔符必须 escape，UTF-8 需要正确折行。不能把敏感电话号码、完整家庭地址或所有社交资料默认导出。示例：

```vcard
BEGIN:VCARD
VERSION:4.0
FN:Alex Chen
N:Chen;Alex;;;
ORG:Robofoto
TITLE:Founder and Product Builder
EMAIL:alex@example.com
URL:https://example.com
END:VCARD
```

**Import**：文件大小限制、mime/扩展名双检查、无效 Unicode/字段容错、重复联系人 UID/name+email 处理；用户确认导入的字段，并决定哪些成为公开模块。对于多联系人 vCard 文件，默认展示选择器，不默默导入所有人。

## 6. 商业后端表（推荐 PostgreSQL）

### product_skus
`sku_id PK, name, price_minor, currency, entitlement_version, edition_id nullable, active, created_at`

### orders
`order_id UUID PK, psp, psp_checkout_id UNIQUE, psp_payment_id UNIQUE nullable, sku_id, quantity, status ENUM('created','paid','refunded','disputed','cancelled'), created_at, updated_at`

### psp_webhook_events
`provider_event_id UNIQUE, event_type, received_at, processed_at, outcome`（请求体脱敏、按风险和合规设置留存）。

### vouchers
`voucher_id UUID PK, order_id FK, voucher_hmac UNIQUE, state ENUM('issued','redeemed','revoked'), created_at, redeemed_at nullable, redemption_id nullable`。不存可再次读取的明文邀请码；用 HMAC-SHA256（服务端 secret）索引随机高熵 token。

### editions
`edition_id PK, name, supply_cap, issued_count, issuer_key_id, immutable_terms_hash, created_at`

### serial_allocations
`edition_id + serial UNIQUE, certificate_id UNIQUE, member_public_key, issued_at, revoked_at nullable`。数据库 `edition` 的 `issued_count` 与 serial allocation 在事务内修改并锁定/约束，超过 cap 必须失败。不要把 `000088` 当成兑换秘密。

### member_certificates
`certificate_id UUID PK, edition_id, serial, member_pubkey, credential_payload_hash, issuer_key_id, issued_at, revocation_status`。签名证书字节可以客户端下载保存；服务端存当前资格状态和最小凭证索引，不存私人卡片的明文内容。

## 7. 会员签发与校验契约

**Voucher secret**：至少 128 bit CSPRNG，base64url 编码，未核销前可视为 bearer secret；只能通过安全通道兑换，不应使用可猜测数字编号代替。用户可自己购买或赠送；转发给他人会让他人有机会提前领取，不宣称“只指定某个收礼人能领”。

**Certificate payload (draft)**：

```json
{
  "format": "neymi-sleeve-cert",
  "version": 1,
  "issuerKeyId": "issuer-2026-01",
  "editionId": "signature-genesis",
  "serial": 88,
  "holderPublicKey": "BASE64URL_PUBLIC_KEY",
  "rights": ["sleeve.genesis", "templates.premium-basic"],
  "issuedAt": "2026-10-24T00:00:00Z"
}
```

对**规范序列化的 bytes**做 Ed25519 等受审查的数字签名，证书需能在离线验证 issuer 公钥时判定完整性和真实性。**持有证书 ≠ 证明拥有私钥**，使用会员权益的高风险操作需挑战签名证明 holder possession。收退款后的实时当前有效性可能需要线上撤销查询；在离线状态下只能验证“曾由发行方签名”。

## 8. API endpoints（推荐 Hono zod-openapi / OpenAPI 契约）

> **安全要求：** 下列 API 不接收个人卡、完整 Profile、Contact/Story、来自接收者的名片文件。定义严格 body allowlist 并覆盖契约测试。

| Method | Path | Request | Response / semantics |
|---|---|---|---|
| GET | `/api/v1/products` | 无 | 仅公开商品与价格/版本/系列限额 |
| GET | `/api/v1/editions/:id` | edition id | series public metadata + issuer key id |
| POST | `/api/v1/checkout` | skuId, quantity (cap), idempotencyKey | PSP hosted checkout URL/order token |
| POST | `/api/v1/webhooks/:psp` | PSP raw signed body | verify signature first; idempotent event handling |
| GET | `/api/v1/orders/:publicToken/vouchers` | 高熵授权 token（短期） | 已支付发放券或可恢复状态；有 rate limit |
| POST | `/api/v1/redeem` | voucher, holderPublicKey, idempotencyKey, proof of possession | one redeemed certificate or deterministic already-redeemed error |
| GET | `/api/v1/issuer-keys` | 无 | public verification keys + key ids |
| GET | `/api/v1/certificates/:id/status` | certificate id | status (without holder PII) |
| GET | `/api/v1/public-feed` | 无 | optional signed release notes; not core MVP |

**安全硬约束：** `GET orders/...` 不能使用可猜测订单号；订单查询令牌需足够随机，安全失效机制及访问策略；付款状态以签名 webhook 为准，前端成功页面仅显示等待确认；兑换 API 具备 IP/令牌双维度限速，不能因为错误细节泄露券拥有者身份。

### 8.1 同时核销事务流程

```
BEGIN;
  SELECT voucher WHERE voucher_hmac=? FOR UPDATE;
  assert state == 'issued';
  validate edition capacity and lock edition row;
  ensure holder pubkey proof is valid;
  UPDATE vouchers SET state='redeemed', redeemed_at=now(), redemption_id=?;
  INSERT serial allocation with UNIQUE (editionId,serial);
  INSERT member certificate intent;
COMMIT;
SIGN canonical certificate payload;
PERSIST signed certificate idempotently;
RETURN signed certificate;
```

**重要**：外部签名调用/持久化失败时，不得令 `redeemed` 永久处于不可恢复的“已经消费但无证书”状态；设计 `redeem_intent / issuance_outbox` 重试状态机或将签名所需材料事务内记录并由可重试作业完成，确保 `redeem` 幂等重放可以安全拿到同一签发结果。涉及多人并发时订单与 series 分配应满足 serial cap。

## 9. 状态机与异常情况

```text
Order: created → paid → vouchers-issued
                 ↘ refunded / disputed
Voucher: issued → redeemed
               ↘ revoked (未兑换前退款/风控)
Issuance: pending → signed → delivered
                    ↘ retryable-failed
Certificate: valid → revoked  (仅线上状态判断；离线签名始终可验)
```

- Webhook 重放：按 `provider_event_id` 唯一处理，订单状态单调变化且能应对乱序。
- 购买后关闭浏览器：允许通过购买凭证恢复 voucher（不要求上传个人名片），但 PSP 邮箱/账单资料可能存在，由支付服务处理。
- 兑换请求中途断网：相同 voucher + holder key + idempotency key 可继续获取同一证书，不能给第二人重复发行。
- 恶意 HTML/JSON：严格内容安全策略，任何接收卡的展示不能使用 raw innerHTML。
- 出厂数据：不得包含虚构可联系的真实 phone/email；测试使用 `example.com` 域及保留测试电话号码段。

# PART 4 — 隐私、安全与发布

# Neymi — 隐私安全边界、风险模型及上线验收 v1.0

> **必须先读：** 产品既要求“无注册、无平台明文托管”，又要求手机号等私人信息可选择性共享。这不是仅靠 localStorage 或 CSS 隐藏字段就能成立的。Codex 不得用未经验证的加密宣传代替安全实施。

## 1. 威胁模型（首版需维护）

| 风险 | 攻击者能做什么 | 防护与真实局限 |
|---|---|---|
| 截获可转发公开文件/链接 | 获取链接并转发、截图 | 公开投影中不含私密字段；公开内容不能承诺仅指定者可见 |
| 恶意浏览器扩展/被入侵设备 | 读取客户端可读数据 | 不是纯 Web 可以彻底消除的风险；加密备份、系统解锁与端点安全建议 |
| 站点 JavaScript 被污染 | 访问本地私密数据或密钥 | 可审计发布、CSP、依赖锁定、可核验离线版；不宣称纯 PWA 天然零知识 |
| 浏览器存储清理 | IndexedDB 被清除 | 加密备份/恢复导出是发布前阻断项，明确备份教育 |
| 共享预览泄露 | OG tags、图片生成服务拿到个人资料 | 预览只允许通用封面或经用户明确批准的公开字段；不在 SSR 中读取私密数据 |
| 静态 Sleeve 伪造 | 复制封套截图或 HTML | 校验证书签名+发行方公钥；证书仅能证明发行真实性 |
| Member token 被盗/他人拿到邀请码 | 盗领或重复领 | ≥128-bit 随机 token、一次性原子核销、限速、签名 holder possession、退款流程 |
| 支付 webhooks 重播/乱序 | 重复发券或越界发行 | 原始 webhook 验签、idempotency keys、数据库事务、唯一约束、可重试签发 |
| 利用 URI 字段注入脚本 | 跳转恶意网页或 XSS | URL allowlist (`https:`)、Zod 校验、输出 escaping、CSP、不信任输入 HTML |
| 号码跨 Persona 追踪 | 把用户工作卡与私人卡串联 | 编号默认可不显示、按 Persona 选择 Sleeve，不自动公开身份公钥 |
| 外部渠道元数据 | 微信/WhatsApp/运营商看到分享行为 | 不承诺平台之外的通信元数据也完全私密 |

## 2. 安全分层与营销文案红线

### M1/MVP 可对外宣称

- 无需注册即可创建与交换**公开或用户已明确授权的**名片资料。
- 资料库主要在本地设备存储；商业服务器不要求接收个人名片明文。
- 支持用户自主导出和受密码保护的加密备份（**仅在真正完成并经测试后**）。
- 分享前选择公开字段，支持手机通讯录导入/导出。

### M1 不可以对外宣称

- “任何分享都是端到端加密”“只有收礼人可以读”“平台永远无法拿到任何数据”“匿名交易完全无法关联”“无论浏览器如何清理都不会丢数据”“随时远程撤回已被看到的信息”。

### M3 后才能按验收结果宣称

- 经身份确认的接收者公钥完成的**指定对象 E2EE**；应提供密钥换机、安全握手、阻断中间人攻击的机制。
- 有明确发布链/可信构建/安全审计范围的客户端可信交付，仍要如实披露 Web 客户端局限。

## 3. 加密方案的开发指导（不要自造算法）

**设备备份**：密码派生优先经审查实现的 Argon2id，随机 salt，适当资源参数；随机对称内容密钥配合 AES-GCM 等成熟 AEAD，文件包含 `format/version/KDF params/salt/nonce/ciphertext`，设置备份密码强度和恢复演练测试。不要用用户姓名/邮箱当密钥。若浏览器环境可用性/性能不合格，应记录兼容替代，不得静默降级为明文。

**本地静态加密的权衡**：若设计成用户打开卡片就能自动看到内容、解密密钥也保存在同一 Web 原点，额外本地 AES 加密对攻击脚本的防护有限。必须明确数据“本机”与“强加密”的不同保障；需要真正静态保密则采用用户解锁操作/受保护存储策略。

**证书签名**：使用发行方 Ed25519 或经过审查的等价算法签名规范序列化结构；客户端通过受信任的公钥验证签名。证书可复制不等于别人拥有权益，消费权益时要有 holder 私钥控制权挑战。

**真正 E2EE（未来项目）**：采用成熟的 HPKE（RFC 9180）实现来加密给接收者的指定内容，密钥认证和元数据保护另行设计，完成多设备、撤销/轮换、反重放测试。不可把解密密钥拼在可随意转发的公开链接里还声称指定人专属。

## 4. 个人数据分享权限的不可变规则

```text
PrivateProfile              [本机]
    └─ SectionVisibility: private | public | recipient-restricted
        └─ Share Preview: select public sections and nested fields
            └─ projectPublicCard(): fresh strictly filtered object
                ├─ Public .ncard / vCard / short #fragment link
                └─ never serializes private sections, unused persona, or full library
```

- `private`：本机仅供自己使用（是否加密静态存储按已实施功能而非口头承诺）。
- `public`：可以被 user 在每次分享时明确选出；任何获得文件的人可读取。
- `recipient-restricted`：MVP **不可通过公开分享方式发送**；待接收者加密功能真正上线后使用。
- 所有可见字段都必须出现在分享前审核界面；允许一次分享只给邮箱而不暴露手机号。
- 只有接收者当前已授权看到的字段才能进入 vCard；截图/打印默认无隐私字段。
- 未明确指定公开的本地 Contact 库绝不全量上传。

## 5. 服务端最小化 / 支付信息

商业 API 允许：随机订单 ID、商品编号、支付平台 transaction reference、券摘要、发行数量、会员公钥、签名证书当前状态与必要的审计字段。

商业 API 禁止：默认 Name/Phone/Email/Story、名片快照、收到的联系人、社交关注/交换图谱、私人密钥、浏览器完整历史。支付提供方可能依法或按业务要求持有付款人 email/账单资料，不宣称绝对匿名。

**可观测性**：不采集“谁把哪张名片发给谁”的关系；优先可选隐私保留统计（例如本地匿名聚合），付款事件单独在商业服务端统计。错误日志 redact voucher secrets / access tokens / request body；限制保存时间。
